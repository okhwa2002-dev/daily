# 보안과 비밀값 규칙

불특정 다수를 대상으로 하는 공개 서비스다. 개인용 프로젝트의 관행을 그대로 가져오지 않는다.

---

## 비밀값

- DB 접속 정보, JWT 시크릿, 메일 발송 계정 등 모든 비밀값은 `.env`에만 둔다. `.env`는 커밋하지 않는다.
- 저장소에는 `.env.example`만 커밋하고, 값 자리에는 형식만 적는다.
- **문서·주석·커밋 메시지에 실제 비밀값을 적지 않는다.** README나 가이드 문서에 "편의상" 비밀번호를 적는 것도 금지한다.
- 비밀값이 저장소에 들어간 것을 발견하면 파일에서 지우는 것으로 끝내지 않고 해당 자격증명을 즉시 교체한다.

---

## 인증

- 비밀번호는 argon2id로 해싱한다. 평문·역산 가능한 형태로 저장하지 않는다.
- 인증이 필요한 모든 라우트는 미들웨어에서 토큰을 검증하고 `userId`를 주입한다.
- 요청 본문·쿼리스트링으로 전달된 사용자 ID는 신뢰하지 않는다. 항상 미들웨어가 주입한 값만 쓴다.
- 로그인 시도는 기록하고, 반복 실패에 대해 제한을 건다.

---

## 로그

- 로그에 비밀번호, 토큰, 세션 값, 이메일 전문을 남기지 않는다.
- 일기 본문·지출 내역 등 사용자 기록 데이터를 로그로 출력하지 않는다. 디버깅이 필요하면 레코드 ID만 남긴다.
- 에러 응답에 스택 트레이스나 SQL 원문을 포함하지 않는다.

**예외: 처리되지 않은 예외의 에러 객체는 전문을 로그에 남긴다.** 전역 에러 핸들러의 catch-all 분기는 `err` 전체를 로깅한다. 장애가 났을 때 에러 메시지가 원인을 가리키는 가장 빠른 단서이고, 메시지를 버리면 재현 불가능한 사고를 추적할 수단이 사라진다.

이 예외가 감수하는 위험은 하나다 — 에러 메시지에 비밀값이 섞여 들어오는 경우(예: 잘못된 `DATABASE_URL`로 인한 드라이버 오류가 접속 문자열 전문을 뱉는 상황). 이건 로그를 막아서가 아니라 **비밀값이 애초에 에러 메시지로 흘러갈 경로를 줄여서** 대응한다. 위 규칙(비밀번호·토큰·세션 값을 직접 로깅하지 않는다)은 그대로 유효하며, 이 예외는 개발자가 의도적으로 남기는 로그가 아니라 예외 객체에만 적용된다.

---

## 개인정보

운동·식사 기록은 건강 관련 정보로 해석될 여지가 있다. 공개 서비스 전제에서 다음을 고려한다.

- 이용약관과 개인정보처리방침이 필요하다.
- 회원 탈퇴 시 데이터 파기 절차가 필요하다. 소프트 삭제와 별개로, 계정 파기는 실제 삭제 또는 비식별화까지 이어져야 한다.
- 수집 항목을 최소화한다. 서비스에 필요 없는 정보는 애초에 받지 않는다.

> 이 항목의 구체적 범위(약관 문안, 파기 주기)는 아직 결정되지 않았다. 공개 배포 전에 확정한다.

# 2단계 구현 계획 — 동기화 엔진 + 지출

설계서 9절의 2단계다. 가장 단순한 도메인(지출)으로 동기화 엔진을 완성하고 검증한다.
엔진이 여기서 검증되면 일기·식사·운동·독서는 레지스트리에 항목을 추가하는 반복 작업이 된다.

**범위에 넣는 테이블은 `expense_categories`와 `expenses` 둘뿐이다.** 나머지 5개 테이블은
스키마만 있는 상태로 남긴다. 엔진이 검증되기 전에 5개를 얹으면 결함이 5배로 번진다.

---

## 착수 전 선행 3건

1단계 최종 리뷰에서 이월된 항목 중 2단계를 막는 것들이다.

### T1 — `normalizeClientTimestamp` (shared)

동기화 push는 클라이언트가 보낸 `updatedAt`을 KST로 정규화해야 하는데 그 함수가 없다.
가장 이름이 비슷한 `fromKstTimestamp`는 오프셋이 붙은 ISO(`2026-08-10T12:00:00+09:00`)를
넣으면 `'...+09:00+09:00'`이 되어 조용히 `Invalid Date`를 낸다.

`Invalid Date`가 그대로 흘러가면 `NaN` 비교가 전부 false가 되어, LWW의
`updated_at < EXCLUDED.updated_at`이 "아무것도 안 덮어씀"으로 퇴화한다.
**사용자 눈에는 "수정이 저장되지 않는다"로 보이고 에러는 어디에도 남지 않는다.**

- 입력: ISO 8601 문자열 (오프셋 유무 무관), 또는 KST 벽시계 문자열
- 출력: KST 벽시계 문자열 `'YYYY-MM-DD HH:mm:ss.SSS'`
- **파싱 실패는 던진다.** 조용한 `Invalid Date`를 만들지 않는 것이 이 함수의 존재 이유다
- 미래 시각 방어: 서버 시각 + 5분을 넘으면 거부한다. 기기 시계가 앞서 있으면 그 레코드가
  영원히 최신이 되어 이후 모든 수정을 이긴다

### T2 — `requireAuth`의 계정 상태 검사

지금은 액세스 토큰의 서명·만료만 본다. 정지·탈퇴 요청된 계정도 토큰이 만료될 때까지
(최대 15분) 그대로 통과한다. 1단계에서는 보호 대상 라우트가 없어 무해했지만,
2단계는 이 훅이 사용자의 건강 기록 전체를 지킨다.

- `users`를 조회해 `status = 'ACTIVE'`이고 `deleted_at IS NULL`인지 확인한다
- 계정이 없으면 `401 UNAUTHORIZED`, 정지·탈퇴 상태면 **`403 ACCOUNT_INACTIVE`**로 구분한다.
  같은 401로 뭉뚱그리면 클라이언트가 토큰 갱신을 시도했다 실패하고 "로그인이 필요합니다"만
  반복해서 보여준다. 유효 서명된 토큰을 이미 가진 요청자에게만 드러나는 정보라 열거 위험이 없다
- 매 요청 DB 조회가 붙는다. 이 규모에서는 인덱스 PK 조회 1회라 문제가 아니다.
  캐시는 "정지가 즉시 반영되지 않는다"를 되살리므로 넣지 않는다

### T3 — 소유권 격리 헬퍼

2단계는 `user_id` 조건이 빠지면 안 되는 쿼리를 대량으로 추가한다. 지금은 헬퍼도
교차 계정 테스트 원형도 없고, 유일한 선례인 `routes/auth.ts`가 라우트에서 `db`를 직접 부른다.

- `ownedBy(table, userId, ...extra)` — `user_id` 조건을 강제로 끼우는 where 빌더
- `liveOwnedBy(...)` — 위 + `deleted_at IS NULL`. 화면 조회용 기본값
- 교차 계정 테스트 원형: 사용자 A의 레코드를 B의 토큰으로 읽기·수정·삭제 시도 → 전부 실패

**FK는 소유권을 검사하지 않는다.** `book_notes.book_id → books.id`는 부모의 존재만
보장하므로, 부모 조회는 반드시 `(user_id, client_uuid)`로 한다.

## 서버

### T4 — 동기화 레지스트리

테이블별 분기를 라우트에 흩뿌리면 테이블을 추가할 때마다 push·pull·검증 세 곳을 고쳐야 하고,
그중 하나를 빠뜨리는 것이 정확히 phase 1에서 반복된 실패 방식이다.

```ts
type SyncTableDef = {
  table: PgTable
  /** 도메인 필드만. 공통 컬럼은 서버가 채운다 */
  payload: z.ZodObject<...>
  /** 부모-자식 동기화가 필요한 테이블만 */
  parent?: {
    idColumn: 'categoryId'
    uuidColumn: 'categoryClientUuid'
    parentTable: PgTable
    /** false면 부모 UUID가 없어도 된다 (지출의 미분류) */
    required: boolean
  }
}
```

**페이로드 스키마는 공통 컬럼을 받지 않는다.** `user_id`, `synced_at`, `created_by`,
`deleted_at`을 클라이언트가 보낼 수 있으면 남의 레코드를 쓰거나 pull 커서를 조작할 수 있다.
zod는 `.strict()`로 두어 모르는 키는 거부한다.

### T5 — `POST /api/sync/push`

```
{ schemaVersion, changes: [{ table, clientUuid, op, updatedAt, payload }] }
→ { results: [{ clientUuid, id, status, serverRow? }], serverTime }
```

항목별로 독립 처리한다. 한 건이 실패해도 나머지는 저장되어야 한다 — 전체 롤백은
"한 레코드가 깨지면 그 기기의 동기화가 영영 막힌다"가 된다.

| 상황 | status | 클라이언트 |
|---|---|---|
| 저장됨 | `APPLIED` | 큐에서 제거 |
| 서버 값이 더 최신 | `STALE` | 큐에서 제거하고 `serverRow`로 로컬 갱신 |
| 부모를 아직 못 찾음 | `CONFLICT` | 큐 유지, 재시도 |
| 알 수 없는 테이블·검증 실패 | `REJECTED` | 큐에서 제거, **사용자에게 알림** |

- 업서트는 `ON CONFLICT (user_id, client_uuid) DO UPDATE ... WHERE updated_at < EXCLUDED.updated_at`
- `RETURNING`이 비면 진 것이다 → 현재 행을 읽어 `STALE`로 돌려준다
- `op: 'DELETE'`도 같은 LWW 규칙을 탄다. 오래된 삭제가 새 수정을 덮으면 안 된다
- `user_id`, `synced_at`, `*_by`는 전부 서버가 채운다. 페이로드 값은 쓰지 않는다
- 배열 순서대로 순차 처리한다. 부모-자식이 같은 배치에 있으면 순서가 곧 보장이다
- 배치 상한을 둔다(500건). 상한이 없으면 요청 하나가 DB를 오래 잡는다

### T6 — `GET /api/sync/pull`

```
?since=<syncedAt>&sinceId=<id>&limit=500
→ { changes: [...], nextCursor: { syncedAt, id }, hasMore }
```

- 커서는 `(synced_at, id)` 복합. `WHERE (synced_at, id) > (:since, :sinceId)`
- 툼스톤도 내려보낸다. 삭제가 전파되지 않으면 다른 기기에 유령 레코드가 남는다
- `nextCursor`는 **실제로 내려보낸 마지막 행**에서 만든다. 서버 현재 시각을 쓰면
  그 사이 커밋된 행을 영구히 건너뛴다

**정착 지연(settling window)이 필요하다.** 트랜잭션은 `synced_at`을 찍는 시점과
커밋 시점이 다르다. `synced_at = T`인 행이 `T+50ms`에 커밋되면, `T+10ms`에 커서 `T`로
돌아간 pull은 그 행을 영영 못 본다 — 커서가 이미 지나가 버렸기 때문이다.

→ `AND synced_at <= now() - interval '1 second'`로 막는다. 1초 이상 걸린 트랜잭션이
있으면 여전히 뚫리지만, 이 규모의 단건 업서트에서는 현실적 위험이 아니다.
대가는 다른 기기 변경이 최대 1초 늦게 보이는 것이고, 폴링 주기가 30초라 무의미한 차이다.

### T7 — 스키마 버전 게이트

PWA는 사용자가 캐시된 구버전을 오래 유지한다. `schemaVersion`이 서버보다 낮으면
`426 Upgrade Required`로 응답하고 클라이언트는 Service Worker 갱신을 유도한다.
이 방어가 없으면 구버전이 잘못된 모양의 데이터를 계속 밀어 넣는다.

## 클라이언트

### T8 — Dexie v2 + 아웃박스 compaction

도메인 테이블(`expenses`, `expenseCategories`)을 버전 2로 추가한다. 인덱스는 `[userId+occurredOn]` 중심.

compaction은 같은 `clientUuid`에 대해:

| 앞 | 뒤 | 결과 |
|---|---|---|
| UPSERT | UPSERT | 마지막 것만 |
| UPSERT | DELETE | DELETE만 |
| (서버 미전송) UPSERT | DELETE | **둘 다 제거** |

- **`seq`는 가장 오래된 항목의 값을 유지한다.** 새 seq를 쓰면 부모보다 자식이 먼저 나간다
- "서버 미전송"은 로컬 레코드에 서버 `id`가 있는지로 판단한다

### T9 — 동기화 엔진

- 트리거: 앱 시작 / `online` 이벤트 / 탭 포커스 복귀 / 30초 주기 / 큐 추가 직후
- 재시도: 일시 실패(네트워크·5xx·CONFLICT)는 지수 백오프 1s→2s→4s…최대 5분, 큐 유지
- 영구 실패(REJECTED)는 큐에서 빼되 **버리지 않는다.** 별도 보관 후 사용자에게 알린다
- **동시 실행 방지.** 30초 타이머와 포커스 복귀가 겹치면 같은 항목을 두 번 밀어 넣는다.
  업서트가 멱등이라 데이터는 안 깨지지만 큐 상태가 꼬인다
- 초기 동기화: `since=0`부터 전량. 완료 전까지 "불러오는 중"을 표시한다.
  부분만 보이면 사용자는 기록 유실로 오해한다

### T10 — 지출 화면

`features/expense/` 아래에 목록·입력·카테고리 관리. **API를 직접 부르지 않는다.**
읽기·쓰기 모두 Dexie를 거치고 `sync/`가 서버 통신을 전담한다.

- 금액은 문자열로 다룬다. 부동소수점 연산을 거치지 않는다
- 가입 시 기본 카테고리 세트(식비/교통/생활/여가/기타)를 로컬에 만들고 큐에 넣는다

### T11 — 미동기화 건수 표시

큐 길이를 항상 보이게 둔다. 이게 없으면 동기화가 조용히 멈춰도 아무도 모른다.

## 필수 테스트 시나리오

설계서 8절에서 가져온다. 이 목록이 통과하지 못하면 2단계는 끝난 것이 아니다.

1. 오프라인 생성 → 온라인 복귀 → 서버 반영
2. 같은 변경 2회 전송 → 중복 행 없음 (멱등)
3. 두 기기에서 같은 레코드 수정 → 나중 `updated_at`이 남음
4. 오프라인 삭제 → 다른 기기에 툼스톤 전파
5. 부모(카테고리) 미전송 상태의 자식(지출) → CONFLICT 후 재시도로 성공
6. pull 페이지 경계에 같은 `synced_at` 다수 → 누락·무한반복 없음
7. 사용자 A의 레코드를 B가 읽기·수정·삭제 시도 → 전부 실패
8. 기기 시계가 앞선 레코드 → 거부되고 이후 수정이 정상 동작

---

## 순서

```
T1 → T2 → T3        선행 (서로 독립, 순서 무관)
T4 → T5 → T6 → T7   서버 (순차)
T8 → T9 → T10 → T11 클라이언트 (순차)
```

서버가 끝나야 클라이언트를 실제로 검증할 수 있다. T8은 서버와 병행 가능하지만
계약(레지스트리 페이로드 스키마)이 확정된 뒤에 시작한다.

# API 일자별 로그 설계

## 목표

API 로그를 `D:\workspace\ok2020\log\daily`에 일자별로 저장하고, 같은 로그를 콘솔에도 출력한다. 모든 로그 레코드는 생성 시각을 포함한 한 줄 형식으로 출력한다.

## 파일 이름과 전환 규칙

- 실행 당일의 파일명은 날짜 없이 `daily-api.log`로 한다.
- 자정이 지나 과거 날짜가 된 파일은 `daily-api-YYYYMMDD.log`로 관리한다. 날짜 구분자는 사용하지 않는다. 예: `daily-api-20260810.log`.
- 로그를 기록할 때마다 현재 날짜를 확인한다. 날짜가 바뀌면 전날의 당일 파일을 날짜 포함 파일명으로 변경하고, 새 `daily-api.log`에 기록을 시작한다.
- 대상 디렉터리가 없으면 애플리케이션 시작 시 생성한다.

## 로거 구성

- Fastify의 Pino 로거에 파일 스트림과 콘솔 스트림을 연결한다.
- 파일과 콘솔 모두 사람이 읽을 수 있는 텍스트 로그를 출력한다. 각 레코드 끝에는 줄바꿈을 넣는다.
- 레코드는 기본적으로 한 줄이되, **값 안에 개행이 있으면 실제 줄바꿈으로 출력한다.** 스택 트레이스를 `\n`으로 escape해 한 줄에 뭉개면 장애 때 읽을 수가 없다. 대신 한 레코드가 여러 줄이 될 수 있으므로 `grep`으로 한 건을 통째로 잡는 것은 포기한다 — 타임스탬프로 시작하는 첫 줄은 여전히 한 줄이다.
- 값에 들어 있던 역슬래시 + `n` 두 글자(사용자 입력)는 줄바꿈으로 바꾸지 않는다. 직렬화 전에 진짜 개행만 표시해 구분을 유지한다.
- 로그 생성 일시는 `YYYY-MM-DD HH:mm:ss` 형식으로 표시한다. 예: `2026-08-11 14:30:05`.
- 기존 로그 레벨 및 `cookie`, `authorization`, `password` 마스킹 규칙을 유지한다.
- 테스트 환경은 기존처럼 로그를 출력하지 않는다.

## 오류 처리

- 로그 디렉터리를 만들거나 파일을 열 수 없으면 서버를 시작하지 않고 원인을 표준 오류로 알린다. 로그 유실 상태로 실행하지 않는다.
- 회전(rename 또는 새 파일 열기) 실패 시에도 기록 대상이 불명확해지지 않도록 오류를 표준 오류로 내보내고, 실패를 호출자에게 전파한다.

## 검증

- 날짜별 파일명 계산: 오늘은 날짜 미포함, 과거 날짜는 `YYYYMMDD` 포함.
- 출력 형식: 레코드마다 마지막 줄바꿈과 `YYYY-MM-DD HH:mm:ss` 생성 일시가 존재.
- 날짜 전환: 전날 당일 파일이 날짜 포함 이름으로 바뀌고, 새 당일 파일이 생성.
- API 기존 테스트, 타입 검사 및 빌드를 실행한다.

# SQL 쿼리 로그

API가 실행하는 SQL을 같은 로그(콘솔 + 일자별 파일)에 남긴다.

## 적용 범위

- **개발환경 전용이다.** `NODE_ENV === 'development'`일 때만 Drizzle에 로거를 붙이고, 그 외 환경에서는 로거 객체를 만들지 않는다.
- 쿼리는 `debug` 레벨로 남긴다. 개발환경의 pino 레벨을 `debug`로 두고 나머지는 `info`를 유지하므로, 켜고 끄는 레버는 레벨 하나로 통일된다.

## 파라미터 마스킹

Drizzle 로거는 SQL 원문과 파라미터 배열만 넘겨준다. 어느 파라미터가 어느 컬럼인지는 알 수 없으므로 **값의 모양으로 판정한다.** 값이 어느 컬럼에서 왔는지에 의존하지 않으므로 새 테이블이 생겨도 규칙이 그대로 유효하다.

| 판정 | 출력 |
|---|---|
| `$argon2`로 시작 | `***argon2***` |
| `^[0-9a-f]{64}$` (sha256 hex) | `***hash***` |
| 이메일 형태 | `u***@example.com` (도메인은 남긴다) |
| 그 외 | 원본 그대로 |

현재 스키마에서 이 규칙이 덮는 값은 `users.password_hash`, `refresh_tokens.token_hash`, `password_reset_tokens.token_hash`, `users.email`이다. 이메일에서 도메인을 남기는 이유는 어느 계정에 대한 쿼리인지 추적은 되어야 하기 때문이다.

## 출력 경로

pino 인스턴스를 `logging/logger.ts`가 소유하고, Fastify와 쿼리 로거가 그것을 함께 쓴다. `pool.ts`는 `buildApp()`보다 먼저 import되므로 로거를 Fastify 안에서 만들면 DB 계층이 접근할 수 없다.

쿼리 로그가 요청 로그와 같은 파일에 섞이는 것이 목적이다. 볼 곳이 둘로 갈리면 요청과 그 요청이 실행한 쿼리를 시간순으로 맞춰볼 수 없다.

**SQL은 남은 필드가 아니라 메시지 자리에 넣는다.** 필드로 넣으면 JSON 직렬화를 거치면서 Postgres가 식별자를 감싼 따옴표가 전부 `\"`로 escape돼 읽을 수 없다. 파라미터는 남은 필드에 그대로 둔다.

## 감수하는 위험

이 로거는 지출 내역·일기 본문 등 **사용자 기록 데이터를 그대로 남긴다.** [security.md](../../../.claude/roles/security.md)의 "사용자 기록 데이터를 로그로 출력하지 않는다"에 대한 예외이며, 개발환경 전용이고 개발 DB에 실사용자 데이터가 없다는 전제 위에서만 성립한다. 개발 환경에서 운영 DB를 바라보는 순간 이 전제가 깨지므로, 위 마스킹 규칙은 개발환경에서도 그대로 적용한다.

## 검증

- 마스킹: argon2 해시·sha256 hex·이메일·평문·비문자열 각각에 대한 단위 테스트.
- 게이팅: `NODE_ENV=test`에서 쿼리 로깅이 꺼져 있고, `development`에서 켜지는지 확인.
- 라우팅: `logQuery`가 마스킹된 파라미터를 공용 로거로 넘기는지 확인.

# 일자별 기록 현황(캘린더) 설계

작성일: 2026-08-14

---

## 1. 목표

한 달을 캘린더로 펼쳐 놓고, **어느 날에 무엇을 기록했는지 한눈에 보이게** 한다. 날짜를 누르면 그날의 지출·운동·독서 기록이 아래에 항목별로 나열된다.

지금까지의 화면은 전부 "한 도메인 × 하루"였다. 지출 화면은 지출만, 운동 화면은 운동만 보여준다. 그래서 "8월에 며칠이나 운동했지", "지난주 목요일에 뭐 했더라" 같은 질문에 답할 자리가 없다. 이 화면이 그 자리다.

**읽기 전용이다.** 수정·삭제·추가는 각 기능 화면이 계속 담당하고, 여기서는 그 화면으로 날짜를 들고 이동만 한다.

### 서버 작업이 없다

필요한 데이터는 이미 전부 로컬 Dexie에 있다. `expenses`·`workouts`·`bookNotes` 셋 다 `[userId+occurredOn]` 인덱스를 갖고 있어 월 범위 조회가 그대로 된다.

**따라서 DB 마이그레이션도, API 라우트 추가도, `SCHEMA_VERSION` 인상도 없다.** 배포 순서 제약(API 먼저, 웹 나중)도 이번에는 걸리지 않는다 — 웹만 올리면 된다.

### 일기·식사는 나중에 붙는다

두 기능이 아직 미착수라 이 화면은 지출·운동·독서 셋으로 시작한다. 붙는 시점에 `loadMonth`에 범위 조회 한 줄과 요약 섹션 하나씩을 더한다. 지금 미리 자리를 파두지 않는다 — 요약의 생김새가 도메인마다 다르다는 것을 (지출은 합계, 운동은 세트, 독서는 인용문) 세 개만 보고 일반화하면 잘못된 인터페이스를 고정하게 된다.

## 2. 데이터 접근 — 캘린더가 자기 조회를 직접 갖는다

이번 작업의 유일한 아키텍처 결정이다. 캘린더는 처음으로 **여러 기능의 데이터를 동시에 필요로 하는 화면**이고, `project-structure.md`가 "통계 화면처럼 여러 기능의 데이터가 필요해지면 그때 필요한 부분만 공용 자리로 뽑아낸다"고 적어둔 지점이다.

**결론: 아무것도 뽑아내지 않는다. `pages/calendar/repository.ts`가 Dexie를 직접 읽는다.**

캘린더가 필요한 질의는 기능 화면의 것과 모양이 아예 다르다. 기능 화면은 "하루치 한 도메인"을 읽지만(`listWorkoutsByDate`), 캘린더는 "한 달치 세 도메인"을 읽어 날짜별로 접는다. 기존 함수를 재사용할 구석이 사실상 없어서, 공용 자리로 승격해 봐야 캘린더가 쓰지 않는 함수까지 함께 끌려간다.

각 `repository.ts`는 읽기와 쓰기가 한 파일에서 같은 헬퍼(`toPayload`, `live`, `newUuid`)를 공유한다. **읽기만 뜯어내면 운동 하나를 고칠 때 열어야 할 파일이 두 폴더로 갈라진다** — "기능 하나는 폴더 하나" 규칙이 정확히 막으려던 왕복이다. 그렇게 해서 없앨 중복은 `live()` 세 줄이 전부다.

`pages/calendar/`는 다른 `pages/<기능>/` 폴더를 임포트하지 않는다. Dexie 스키마(`src/db/`)와 코드 캐시(`src/codes/`)는 이미 공용 자리이므로 그대로 쓴다.

### 검토했으나 택하지 않은 두 가지

**읽기 함수를 `src/records/`로 승격** — 위에 적은 이유로 기각. 얻는 것이 `live()` 하나인데 기능 폴더가 갈라진다.

**각 기능이 요약 제공자를 export, 캘린더가 레지스트리로 조립** — 확장성은 제일 좋지만 캘린더가 세 기능 폴더를 모두 임포트해야 해서 규칙을 정면으로 어긴다. 도메인 3개에 추상 계층을 세우는 것은 요약의 생김새가 도메인마다 다르다는 사실을 아직 모른 채 인터페이스를 고정하는 일이다.

### `live()`는 `src/db/`로 올린다

지출·독서·운동 세 파일에 아래 세 줄이 똑같이 복사돼 있고 캘린더가 네 번째 사용처다.

```ts
function live<T extends { deletedAt: string | null }>(rows: T[]): T[] {
  return rows.filter((row) => row.deletedAt === null)
}
```

"두 번째 사용처가 실제로 생겼을 때 뽑는다"는 기준을 이미 한참 지났다. 순수 함수를 옮기고 세 곳이 임포트하도록 바꾸는 것뿐이라 동작은 변하지 않는다.

## 3. 파일 구조

```
apps/web/src/
├── db/index.ts                 live() 추가 (기존 세 곳에서 이관)
├── App.tsx                     / → 캘린더, /expenses → 지출
├── components/TabBar.tsx       홈 / 지출 / 독서 / 운동
├── pages/calendar/
│   ├── CalendarPage.tsx        월·선택날짜 상태, 데이터 구독, 조립
│   ├── MonthGrid.tsx           7열 격자와 점
│   ├── DaySummary.tsx          선택한 날의 항목 나열
│   ├── month.ts                격자 날짜 계산 (순수 함수)
│   └── repository.ts           월 범위 조회 + 날짜별 집계
├── pages/expense/ExpensePage.tsx   ?date= 초기값
└── pages/workout/WorkoutPage.tsx   ?date= 초기값
```

`month.ts`를 `MonthGrid.tsx`에서 분리하는 이유는 성격이 다르기 때문이다. 격자 계산(그 달 1일의 요일, 일수, 앞 빈칸 개수)은 오프바이원이 나오는 자리라 단위 테스트가 촘촘히 붙어야 하는데, 컴포넌트 파일에 두면 렌더 테스트와 섞인다.

`repository.ts`에 두지 않는 것도 같은 이유다 — 그 파일은 DB 접근 자리고, 날짜 계산은 DB를 모른다.

### 라우팅

| 경로 | 화면 | 탭바 |
|---|---|---|
| `/` | `CalendarPage` | 있음 |
| `/expenses` | `ExpensePage` | 있음 |
| `/books` | `BookListPage` | 있음 |
| `/books/:clientUuid` | `BookDetailPage` | 없음 |
| `/workouts` | `WorkoutPage` | 있음 |

지출이 `/`에서 `/expenses`로 밀린다. 캘린더가 홈인 이유는 앱을 열었을 때 먼저 보여야 하는 것이 "오늘 뭘 기록해야 하나 / 이번 달 어떻게 지냈나"이기 때문이다.

`TabBar`의 `TABS` 배열에 홈이 앞에 붙어 넷이 된다. `NavLink`의 `end`가 이미 걸려 있어 `/`가 다른 경로에서 활성으로 잡히지 않는다.

## 4. 월 로딩 — 한 번 읽어 격자와 상세를 모두 먹인다

```ts
export interface DayRecords {
  expenses: LocalExpense[]
  workouts: LocalWorkout[]
  bookNotes: LocalBookNote[]
}

/** key는 'YYYY-MM-DD'. 기록이 하나도 없는 날은 키 자체가 없다 */
export type MonthRecords = Map<string, DayRecords>

/** month는 'YYYY-MM' */
export async function loadMonth(userId: number, month: string): Promise<MonthRecords>
```

세 테이블을 `[userId+occurredOn]` 범위로 병렬 조회하고, `live()`로 툼스톤을 걷어낸 뒤 날짜별로 접는다.

**격자의 점도, 선택한 날의 상세도 이 Map 하나에서 나온다.** 날짜를 눌러도 추가 조회가 일어나지 않고, 조회는 월을 넘길 때만 생긴다. 한 달치 세 도메인은 인덱스 범위 스캔으로 수백 행 수준이라 통째로 들고 있어도 부담이 없다.

### 범위 상한은 항상 31일로 잡는다

```ts
const from = `${month}-01`
const to = `${month}-31`
```

그 달의 마지막 날을 계산하지 않는다. 날짜가 문자열이라 사전순이 곧 시간순이고 `'2026-02-28' < '2026-02-31'`이므로, 상한만 넉넉하면 2월도 30일 달도 전부 잡힌다. **윤년·월말 계산 자체를 없앤다.** `workout/repository.ts`의 `DATE_MIN`/`DATE_MAX`와 같은 수법이다.

### 라벨에 필요한 두 가지

| 필요한 것 | 어디서 | 왜 |
|---|---|---|
| 지출 카테고리명 | `db.expenseCategories` 직접 조회 | `pages/expense/`를 임포트하지 않는다 |
| 운동 부위·강도 라벨 | `src/codes/`의 `listCodes` + `codeLabel` | 코드 캐시는 이미 공용 자리다 |

카테고리 조회는 `listCategories`와 같은 질의지만 캘린더가 자기 것을 갖는다. 지출 폴더를 임포트하는 순간 §2의 결정이 무너진다.

### 구독

```ts
const records = useLiveQuery(() => loadMonth(userId, month), [userId, month], new Map())
```

기존 화면과 같은 모양이다. `useLiveQuery`가 세 테이블의 변경을 deps와 무관하게 스스로 추적하므로, 다른 탭에서 기록을 저장하거나 서버에서 pull이 들어오면 캘린더가 알아서 다시 그려진다.

## 5. 화면

### 격자

일요일 시작 7열. 앞뒤 달의 날짜는 빈칸으로 둔다 — 흐리게 채워 넣으면 누를 수 있는 것처럼 보이는데, 누르면 달이 바뀌어야 할지 그 자리에서 요약을 보여줘야 할지가 애매해진다. 빈칸이면 그 질문이 생기지 않는다.

각 칸은 날짜 숫자 아래에 점 세 개 자리(지출·운동·독서)를 두고 **기록이 있는 도메인만** 점을 찍는다. 오늘은 테두리로, 선택한 날은 채운 배경으로 구분한다.

**점은 색으로만 구분되므로 날짜 버튼의 `aria-label`이 정보를 문장으로 담는다.**

```
aria-label="8월 14일, 지출·운동 기록"
aria-label="8월 11일, 기록 없음"
```

색각 이상 사용자와 스크린리더 사용자가 모두 여기서 읽는다. 점의 색만으로 도메인을 구분하게 두면 이 화면의 목적("한눈에")이 일부 사용자에게 성립하지 않는다.

### 월 이동과 선택

헤더에 `‹ 2026년 8월 ›`와 "오늘" 버튼을 둔다. "오늘"은 이번 달로 돌아오면서 오늘을 선택까지 한다 — 그 버튼을 누르는 의도가 "오늘 뭘 기록했는지 보자"이지 "이번 달 격자를 보자"가 아니기 때문이다.

**월을 넘기면 선택을 해제한다.** 새 달의 1일이나 같은 일자를 대신 고르면 사용자가 고른 적 없는 날을 고른 척하게 된다. 선택이 없을 때는 요약 자리에 "날짜를 선택하세요" 안내만 둔다.

(`WorkoutPage`가 날짜를 바꿀 때 수정 중이던 폼을 버리는 것과 같은 판단이다 — 화면의 두 부분이 서로 다른 날짜를 가리키는 상태를 애초에 만들지 않는다.)

첫 진입 시에는 이번 달을 열고 오늘을 선택해 둔다.

### 요약

지출 → 운동 → 독서 순으로 섹션. 각 섹션은 헤더에 집계(지출은 합계, 나머지는 건수)를 달고, 아래에 항목을 한 줄씩 나열한다.

기록이 없는 도메인의 섹션은 아예 렌더하지 않는다. 세 도메인 모두 없으면 "이 날은 기록이 없습니다."

**섹션 헤더 오른쪽에 그 기능 화면으로 가는 링크를 두되, 보고 있던 날짜를 넘긴다.**

```
/expenses?date=2026-08-14
/workouts?date=2026-08-14
```

이게 없으면 "지출 ›"을 눌렀는데 오늘 기록이 뜬다. 대신 두 페이지가 초기 날짜를 쿼리스트링에서 읽도록 각각 고쳐야 한다 — **캘린더 폴더 밖을 건드리는 유일한 변경이다.**

형식이 `YYYY-MM-DD`가 아니면 조용히 오늘로 떨어뜨린다. 캘린더가 넘기는 값은 항상 정상이지만 URL은 사용자가 고칠 수 있고 북마크는 낡는다.

`BookListPage`는 날짜별 화면이 아니라 책 목록이다. `?date=`를 받아도 쓸 자리가 없으므로 **독서 섹션의 링크는 날짜를 넘기지 않고 `/books`로만 간다.** 감상평은 책 상세 안에 있어 날짜로 좁힐 대상이 아니다.

### 운동 세트 포맷은 `src/lib/`로 올린다

`WorkoutPage`에 `60kg×10, ×12`로 줄이는 `formatSets`가 이미 있다. 처음에는 캘린더가 자기 것을 새로 갖는 쪽을 택했지만, 구현해보니 두 화면의 요약이 결국 같은 모양이 됐다 — `formatSets`·`formatCardio` 모두 두 파일에서 한 글자도 다르지 않았다.

같은 함수가 화면마다 따로 구현되면 한쪽에서 조용히 깨질 수 있는 규칙(`sets`가 null인 근력 기록, `durationMin`이 null인 유산소 기록에 대한 방어)을 갖고 있다는 점에서 §2의 `live()`와 성격이 같다. 그래서 `live()`, `money.ts`와 같은 이유로 `apps/web/src/lib/workoutFormat.ts`로 승격했다. `src/lib/`는 이미 공용 자리이므로 "기능 폴더를 임포트하지 않는다"는 규칙도 그대로 지켜진다 — 임포트되는 것은 기능 폴더가 아니라 공용 자리다.

`sets`가 null인 근력 기록과 `durationMin`이 null인 유산소에 대한 방어는 승격한 함수 안에 그대로 남는다. `apply.ts`가 서버 페이로드를 재검증 없이 Dexie에 쓰므로 이 방어는 화면단 검증을 거치지 않은 값이 그대로 들어올 수 있는 한 계속 필요하다.

## 6. 로딩과 빈 상태

쓰기가 없어서 에러 표면이 작다. 저장 실패도, 아웃박스도, 충돌도 이 화면에는 없다.

**초기 동기화 전의 빈 달**만 실제로 다뤄야 한다. 기록이 아직 내려오지 않은 상태에서 빈 격자를 그대로 보여주면 사용자는 기록이 사라졌다고 읽는다. 기존 화면과 같이 `SyncStatus`를 상단에 두고, `initialSyncDone`이 false인 동안 "기록을 불러오는 중입니다…" 배너를 띄운다.

`useLiveQuery`의 초기값은 빈 `Map`이다. 기존 화면들이 빈 배열을 쓰는 것과 같은 선택이고, 로딩 중 빈 화면이 잠깐 보이는 문제는 위 배너가 담당한다.

## 8. 범위 밖

| 항목 | 이유 |
|---|---|
| 차트·통계 집계 | 통계는 별도 화면으로 예정돼 있다. 캘린더는 "무엇을 기록했나"까지다 |
| 주·연 단위 보기 | 월 하나로 시작한다. 필요해지면 그때 |
| 이 화면에서의 편집 | 각 기능 화면이 계속 담당한다. 폼을 여기서 다시 끌어쓰면 결합이 커진다 |
| 일기·식사 자리 미리 파두기 | §1에 적은 이유. 붙을 때 한 줄씩 더한다 |
| 서버 집계 API | 로컬에 데이터가 다 있다. 서버를 부르면 데이터 소스가 둘이 된다 |

# 마이 탭 레이아웃 설계

작성일: 2026-08-14

---

## 1. 목표

하단 탭을 **홈·마이 둘로 줄인다.** 지출·독서·운동은 각자 탭을 갖는 대신 마이 화면의 카드 세 장이 되고, 카드를 누르면 그 기능의 등록 화면으로 들어간다.

지금 탭바는 홈·지출·독서·운동 넷이다. 일기·식사가 붙으면 여섯이 되고, 통계까지 붙으면 일곱이다. 하단 탭은 그렇게 늘어날 수 있는 자리가 아니다 — 폭이 좁아지면 라벨이 뭉개지고, 무엇보다 "탭 = 기능 하나"라는 구조가 기능 수만큼 앱의 첫 화면을 쪼갠다.

**마이 화면이 그 확장을 흡수한다.** 일기·식사가 붙으면 탭이 아니라 카드가 한 장씩 늘어난다.

### 캘린더와 역할이 어떻게 다른가

둘 다 여러 도메인을 가로질러 읽지만 묻는 질문이 다르다.

| 화면 | 질문 | 축 |
|---|---|---|
| 홈(캘린더) | "언제 뭘 기록했나" | 한 달 × 세 도메인, 날짜를 고른다 |
| 마이 | "오늘 뭘 기록했고, 지금 뭘 기록할까" | 오늘 × 세 도메인, 기능을 고른다 |

캘린더는 날짜가 주인이라 지난 날을 되짚는 데 쓰이고, 마이는 기능이 주인이라 **등록 화면으로 들어가는 입구**다. 그래서 마이는 항상 오늘만 본다 — 날짜 선택기를 두면 캘린더와 같은 화면이 두 개가 된다.

### 서버 작업이 없다

필요한 데이터는 전부 로컬 Dexie에 있고 인덱스도 이미 있다(`expenses`·`workouts`의 `[userId+occurredOn]`, `books`의 `[userId+status]`).

**DB 마이그레이션도, API 라우트 추가도, `SCHEMA_VERSION` 인상도 없다.** 웹만 올리면 된다.

## 2. 내비게이션 — 탭과 안쪽 화면을 가른다

이번 작업의 핵심 결정이다. 지출·독서·운동 화면은 **탭이 아니라 마이 탭 안쪽 화면**이 된다.

| 경로 | 화면 | 탭바 |
|---|---|---|
| `/` | `CalendarPage` | 있음 |
| `/my` | `MyPage` | 있음 |
| `/expenses` | `ExpensePage` | **없음** |
| `/books` | `BookListPage` | **없음** |
| `/books/:clientUuid` | `BookDetailPage` | 없음 (지금도 없다) |
| `/workouts` | `WorkoutPage` | **없음** |

URL은 하나도 바뀌지 않는다. 캘린더의 `DaySummary`가 내보내는 `/expenses?date=`·`/workouts?date=`·`/books` 링크가 그대로 살아 있고, 목적지 화면이 계층상 한 칸 내려갔을 뿐이다.

**안쪽 화면에 탭바를 남기지 않는 이유는 `TabBar` 주석이 이미 적어둔 것과 같다** — 안쪽에서 다른 탭으로 바로 나가면 돌아올 자리를 잃는다. 여기에 하나가 더해진다: 마이 탭 안에서 "마이" 탭을 누르는 상태가 생긴다. 그게 현재 위치로의 이동인지 목록으로의 복귀인지 사용자도 코드도 답을 갖고 있지 않다.

### 뒤로 버튼 — `components/BackHeader.tsx`

새로 안쪽으로 내려가는 세 화면(지출·독서·운동)이 같은 헤더를 쓴다. `‹` 버튼과 제목뿐이다.

```tsx
interface Props {
  title: string
}
```

**돌아갈 곳은 히스토리가 있으면 `navigate(-1)`, 없으면 `/my`다.**

```ts
const location = useLocation()
const hasHistory = location.key !== 'default'
```

`/my` 하나로 고정하면 홈의 "자세히"를 눌러 들어온 사용자가 홈이 아닌 마이에 떨어진다. 반대로 `navigate(-1)`만 쓰면 PWA를 새로 열거나 북마크로 직접 진입했을 때 히스토리가 비어 앱 밖으로 나간다. 두 경우가 실제로 다 생기므로 둘 다 다룬다.

`location.key`는 히스토리 스택의 첫 항목에서 `'default'`다. React Router가 주는 값이라 `window.history.length`를 세는 것보다 정확하다 — 그 길이는 앱 밖에서 쌓인 항목까지 포함한다.

**`BookDetailPage`는 건드리지 않는다.** 지금도 안쪽 화면이고 `navigate('/books')`로 정상 동작한다. 헤더 모양도 다르다 — 라벨이 "← 목록"으로 더 구체적이고, 제목 없이 오른쪽에 수정·삭제 버튼이 붙어 있다. 여기에 제목을 요구하는 공용 헤더를 끼우면 본문의 책 제목과 중복되고, 그걸 피하려고 `title`을 선택 인자로 만들면 세 화면이 쓰는 계약이 흐려진다.

### 탭바

```ts
const TABS = [
  { to: '/', label: '홈' },
  { to: '/my', label: '마이' },
] as const
```

배열만 줄인다. `NavLink`의 `end`가 이미 걸려 있어 `/`가 `/my`에서 활성으로 잡히지 않는다.

## 3. 마이 화면

### 파일 구조

```
apps/web/src/
├── components/
│   ├── TabBar.tsx          홈 / 마이
│   └── BackHeader.tsx      신규 — ‹ 뒤로 + 제목
└── pages/my/
    ├── MyPage.tsx          데이터 구독, 카드 조립, 계정 영역
    ├── SummaryCard.tsx     카드 한 장의 껍데기 (링크·제목·요약·미리보기)
    └── repository.ts       오늘 지출·운동 + 읽는 중 책
```

`SummaryCard.tsx`를 나누는 이유는 카드 세 장이 안쪽 내용만 다르고 껍데기가 같기 때문이다. 카드가 링크라는 사실(누르는 영역, 포커스 링, 화살표 위치)이 세 곳에 복사되면 일기·식사가 붙을 때 다섯 벌이 된다.

`pages/my/`는 다른 `pages/<기능>/` 폴더를 임포트하지 않는다. `src/db/`·`src/lib/`·`src/components/`는 이미 공용 자리이므로 그대로 쓴다 — 캘린더가 세운 선례와 같다.

### 데이터 접근

```ts
export interface TodayRecords {
  expenses: LocalExpense[]
  workouts: LocalWorkout[]
  /** 상태가 READING인 책. 날짜와 무관하다 */
  readingBooks: LocalBook[]
}

export async function loadToday(userId: number, date: string): Promise<TodayRecords>
```

한 번 읽어 카드 세 장을 모두 먹인다. `useLiveQuery(() => loadToday(userId, today), [userId, today], EMPTY)` 한 줄로 구독하면 다른 화면에서의 저장도 서버 pull도 자동으로 반영된다.

`loadMonth`와 질의 모양이 다르다. 캘린더는 "한 달 범위 × 세 도메인"을 날짜별로 접지만 여기는 "오늘 하루 × 두 도메인 + 상태로 고른 책"이다. 특히 **독서는 축 자체가 다르다** — 캘린더는 그날 쓴 감상평(`bookNotes`)을 세지만 마이는 지금 읽고 있는 책(`books.status === 'READING'`)을 본다. 오늘 감상평을 안 썼다고 읽는 중인 책이 사라지면 안 된다.

`live()`로 툼스톤을 걷어내는 것은 세 질의 모두 동일하다.

### 카드 내용

| 카드 | 요약(제목 옆) | 미리보기 | 이동 |
|---|---|---|---|
| 지출 | 오늘 합계 (수입 +, 지출 −) | 메모가 있는 항목의 메모, 최대 3줄 | `/expenses?date=오늘` |
| 독서 | 읽는 중 N권 | 책 제목, 최대 3줄 | `/books` |
| 운동 | 오늘 N건 | 운동 이름, 최대 3줄 | `/workouts?date=오늘` |

순서는 지출 → 독서 → 운동으로 고정한다.

합계는 `DaySummary`와 같이 최소 단위 정수(`bigint`)로 누적한다. `toMinorUnits`·`formatMinorUnits`가 이미 `src/lib/money.ts`에 있다.

`/books`에는 날짜를 넘기지 않는다. 책 목록은 날짜별 화면이 아니라서 `?date=`를 받아도 쓸 자리가 없다 — 캘린더가 이미 같은 판단을 했다.

### 지출 카테고리 이름은 조회하지 않는다

`pages/expense/`와 `pages/calendar/`가 각각 카테고리 이름 맵 조회를 갖고 있다. 마이가 카테고리를 보여주려면 세 번째 사본이 생긴다.

**보여주지 않는 쪽을 택한다.** 카드는 "핵심만"이 요구사항이고, 합계·건수·메모까지면 오늘 뭘 썼는지 판단하는 데 충분하다. 카테고리별 내역은 카드를 눌러 들어간 지출 화면이 이미 보여준다. 공용 자리로의 승격은 세 번째 실사용처가 정말 필요해질 때 판단한다 — 지금 뽑으면 승격 근거가 "쓰지도 않을 화면이 하나 더 생겼다"가 된다.

같은 이유로 운동의 부위·강도 라벨(`src/codes/`)도 카드에서는 읽지 않는다. 이름만 나열한다.

### 빈 카드도 남긴다

기록이 없는 카드는 숨기지 않고 "오늘 기록이 없습니다"를 미리보기 자리에 둔다.

캘린더의 `DaySummary`는 빈 섹션을 렌더하지 않는다. 그 화면은 읽기 전용이라 빈 섹션이 자리만 차지하기 때문이다. **마이는 반대다** — 카드가 곧 등록 화면으로 가는 입구라서, 카드가 사라지면 기록하러 들어갈 길도 같이 사라진다. 오늘 아직 아무것도 안 한 사용자가 이 화면에서 가장 필요로 하는 것이 그 입구다.

### 계정 영역

카드 아래에 이메일과 로그아웃 버튼을 둔다.

로그아웃은 지금 `ExpensePage` 헤더에만 있다. 지출이 탭에서 빠지면 안쪽 화면 하나에 묻히므로 마이로 옮긴다. `logoutSafely`·`stopSync` 호출과 미동기화 건수 확인 문구는 그대로 옮겨오고, `ExpensePage`에서는 걷어낸다.

**이메일을 표시한다.** `session.user`는 `{ id, email }`만 갖고 있어 로그인 아이디가 클라이언트에 없다. 아이디를 보여주려면 서버 응답을 늘려야 하는데 이번 범위 밖이다.

### 로딩

`SyncStatus`를 상단에 두고 `initialSyncDone`이 false인 동안 "기록을 불러오는 중입니다…" 배너를 띄운다. 기존 네 화면과 같은 모양이다.

빈 카드와 로딩 중 카드가 똑같이 "기록이 없습니다"로 보이면 안 되므로, 배너가 그 구분을 담당한다.

### 여백

탭바가 있는 화면(`/`, `/my`)은 `pb-20`을 유지하고, 안쪽 화면 셋(`/expenses`·`/books`·`/workouts`)에서는 뺀다. 탭바가 없는데 하단 여백만 남으면 목록 끝에 빈 공간이 뜬다.

### 문서 갱신

`CLAUDE.md`의 설계 문서 목록에 이 문서를 더한다. 기능 상태표는 바뀌지 않는다 — 지출·독서·운동은 그대로 완료고, 이번 작업은 그 화면들에 닿는 경로만 바꾼다.

프로젝트 관행대로 테스트를 먼저 쓴다.

| `pages/my/repository.test.ts` | 오늘만 조회(어제·내일 제외), 툼스톤 제외, 다른 사용자 격리, `READING`이 아닌 책 제외, 기록이 없을 때 빈 배열 |
| `pages/my/MyPage.test.tsx` | 카드 3장이 지출·독서·운동 순, 합계 부호(수입/지출), 링크 목적지의 `?date=`, 독서 링크에 날짜 없음, 빈 카드 문구, 로그아웃 |
| `components/BackHeader.test.tsx` | 히스토리가 있으면 `-1`, 없으면 `/my`, 제목 렌더 |
| `components/TabBar` | 탭이 홈·마이 둘, `/`가 `/my`에서 활성이 아님 |
| 기존 `ExpensePage.test.tsx` | 로그아웃 관련 케이스 제거(마이로 이관), `?date=` 초기값은 그대로 |

`App.tsx` 라우팅 변경이 기존 페이지 테스트에 영향을 주는지는 구현 시 확인한다.

## 5. 범위 밖

| 항목 | 이유 |
|---|---|
| 홈(캘린더) 화면 변경 | 사용자 요청이 "홈 탭은 그대로"다. 링크 목적지도 안 바뀐다 |
| 마이 화면에서의 편집·등록 | 카드는 입구다. 폼을 여기서 끌어쓰면 마이가 세 기능의 입력 로직에 묶인다 |
| 마이 화면의 날짜 선택기 | 지난 날을 되짚는 것은 홈의 역할이다. §1 참고 |
| 카테고리 이름 조회의 공용 승격 | §3에 적은 이유 |
| 프로필 수정·비밀번호 변경 | 계정 복구 기능 자체가 아직 미착수다. 자리만 미리 파두지 않는다 |
| 일기·식사 카드 자리 미리 파두기 | 붙을 때 `SummaryCard` 한 장과 `loadToday` 질의 한 줄을 더한다 |
